## Blocking - must fix before merge

- [ ] `src/auth/session-store.ts:136` + `src/auth/crypto.ts:112` - **forceNew deletes key.dpapi but the v2 key stays cached in memory**
  **Problem:** `clearAllLocalData()` does `rmSync(CONFIG_DIR)`, which now also removes `key.dpapi`. `getV2Key()` returns the cached `v2Key` and never notices. The long-running MCP server then writes the fresh session as v2 with a key that exists nowhere on disk. Next process start → no key file → new random key → GCM auth failure → `readSecure` returns null → the login the user just did is lost. Same staleness across processes (CLI `login --force` while the server runs). Reproduced with a stub protector by two reviewers.
  **Fix:** export `resetKeyCache()` (sets `v2Key = undefined`) from crypto.ts and call it right after the `rmSync` in `clearAllLocalData()`. Test: encrypt → rm dir → encrypt → reset cache (simulated new process) → decrypt succeeds.

- [ ] `src/auth/crypto.ts:118-133` - **Any getV2Key failure is cached as 'unavailable' for the process lifetime**
  **Problem:** three triggers, one bad outcome. (1) Two processes on first run both see no key file; the loser's `writeFileSync(..., {flag:'wx'})` throws EEXIST. (2) A reader hits the file between `wx` create and write and gets `''`. (3) A transient PowerShell failure/30s timeout. All land in the generic catch → `v2Key = 'unavailable'` forever. That process then cannot decrypt any v2 file (`readSecure` → null → looks signed out → auto-login) and every write silently downgrades the file to v1 (hostname+username key). Fail-open, and it flips v1/v2 back and forth with the other process. Race reproduced.
  **Fix:** on EEXIST, re-read and unprotect the existing file. Create atomically (write `keyPath.<pid>.tmp`, `fs.linkSync` to `keyPath`, unlink tmp). Do not cache unprotect/timeout failures - retry on next call (or after a backoff). Never write v1 over an existing v2 file when a protector is configured; only allow v1 when `keyProtector === null`.

- [ ] `src/auth/crypto.ts:69` - **powershell.exe launched by bare name → binary planting from CWD**
  **Problem:** `execFileSync('powershell.exe', ...)`. On Windows libuv searches the current working directory before PATH. Confirmed by a reviewer: a renamed `whoami.exe` as `powershell.exe` in the cwd ran instead of PowerShell. Server/CLI started from an untrusted directory → arbitrary code execution, and on first-key creation the raw AES key is handed to it on stdin. A security-hardening PR must not add this.
  **Fix:** `path.join(process.env.SystemRoot ?? 'C:\\Windows', 'System32', 'WindowsPowerShell', 'v1.0', 'powershell.exe')`, plus `cwd: process.env.SystemRoot`. Add a test asserting the executable path is absolute.

## Warning - should fix

- [ ] `AGENTS.md:161` + `src/auth/crypto.ts:12-16` - **Offline-theft claim overstated**
  **Problem:** "the key cannot be unwrapped on another machine or account" is false: CONFIG_DIR is in Roaming `%APPDATA%`, DPAPI master keys roam with it, and the user's password or the domain DPAPI backup key unwraps a backup offline. Worse, the long-lived credential (MSAL refresh token) sits unencrypted in `browser-profile/` localStorage in the same directory, so copying the config dir still yields it. The encryption protects derived copies, not the crown jewel.
  **Fix:** reword both passages: DPAPI ties `session-state.json`/`token-cache.json` to the user's logon secret; `browser-profile/` (refresh token) is not covered; no protection against same-user processes, roaming profiles, or holders of the password/domain backup key.

- [ ] `src/auth/session-store.ts:76-84` - **v1→v2 migration writes on the read path, non-atomically**
  **Problem:** `writeSecure` is truncate-and-write. Migration can overwrite tokens another process just refreshed (lost update), and a concurrent reader can see a truncated file → null → auto-login. Happens on first start after upgrade, exactly when server + CLI are both likely running.
  **Fix:** make `writeSecure` atomic (tmp file with 0o600 + `renameSync`). Before migrating, re-read and skip if the on-disk blob changed (compare iv/tag).

- [ ] `src/api/graph-files-api.ts:112` - **Containment checked on realpath, write done on the unresolved path later**
  **Problem:** `resolveOutputPath` validates `realpath(dirname(dest))` but returns raw `dest`; `open(..., 'wx')` runs seconds later after the token + Graph calls. A parent component swapped for a junction/symlink in between escapes the root. Low exploitability (needs write access to the root), but the doc claims escapes are rejected.
  **Fix:** return `join(parentReal, basename(dest))` and write to that; re-check containment immediately before `open()`.

- [ ] `src/tools/message-tools.ts:204,244,449` - **Removal tools marked `destructiveHint: false`**
  **Problem:** MCP spec: `destructiveHint: false` means "only additive updates". `teams_remove_favorite`, `teams_unsave_message`, `teams_remove_reaction` remove state. Clients auto-approving non-destructive tools will run them silently; `annotations.test.ts` locks in the wrong set.
  **Fix:** `destructiveHint: true` (+ `idempotentHint: true`) on all three; add them to `DESTRUCTIVE_TOOLS` in the test.

- [ ] `src/auth/token-refresh-http.ts:350` - **Error-body cap not applied where the big bodies are**
  **Problem:** commit claims error bodies in logs are capped, but the OAuth refresh path embeds the full Azure AD body: `` errorDetail = `${errorJson.error}: ${errorText}` `` - uncapped, logged. `MAX_ERROR_BODY_CHARS` doc ("kept in error messages (and therefore logs)") reads as global.
  **Fix:** shared `truncateErrorBody()` next to the constant, used in http.ts and token-refresh-http.ts; or narrow the doc to `httpRequest()`.

- [ ] `vitest.config.ts:8` / `src/__fixtures__/isolated-key-store.ts` - **"Tests never touch the real config dir" is false**
  **Problem:** the setup file isolates only `key.dpapi`. `CONFIG_DIR` still resolves to the real `%APPDATA%\teams-mcp-server`; a reviewer showed `auth-guards.test.ts` (unmocked `clearTokenCache()`) deletes the real `token-cache.json`. Pre-existing, but this PR claims the isolation.
  **Fix:** point `APPDATA`/`HOME`/`USERPROFILE` at a per-run temp dir via `test.env` + globalSetup so `paths.ts` evaluates against it; assert `CONFIG_DIR` is not under the real home. Or correct the claim.

- [ ] `src/auth/crypto.ts:71` - **Magic timeout `30000`**
  **Problem:** DPAPI call timeout hardcoded; it also blocks the event loop synchronously inside encrypt/decrypt.
  **Fix:** `export const DPAPI_CALL_TIMEOUT_MS = 30_000;` in constants.ts.
  **Rule:** "Magic numbers (page sizes, timeouts, thresholds) live in `constants.ts`."

- [ ] `docs/MANUAL-TEST-SCRIPT.md:188,227` - **Manual download steps now fail**
  **Problem:** steps use `outputPath="/tmp/file.docx"` / `"/tmp/lesson.pptx"`, now rejected with INVALID_INPUT. Step 5 ("must fail, never overwrites") then passes for the wrong reason.
  **Fix:** use relative names (`file.docx`, `lesson.pptx`); add a step that an absolute path outside the root fails.
  **Rule:** "For manual testing of all tools, see `docs/MANUAL-TEST-SCRIPT.md`."

- [ ] `docs/SESSION-DATA-REFERENCE.md:463-471` - **Encryption reference still describes only the hostname+username key**
  **Problem:** contradicts the updated AGENTS.md; no `key.dpapi` in its file list (also missing from README "Session Files").
  **Fix:** mirror the (corrected) AGENTS.md encryption paragraph; add `key.dpapi` to both file lists.

- [ ] `AGENTS.md` (Extending > New tool) - **Recipe omits now-mandatory annotations**
  **Problem:** `annotations.test.ts` fails any tool without boolean `readOnlyHint`/`destructiveHint`; destructive tools must also be added to `DESTRUCTIVE_TOOLS`. Following the documented recipe gives a red suite.
  **Fix:** add both requirements to the New tool paragraph.

## Nit - optional but worth it

- [ ] `src/utils/http.ts:143` - **Classifier gets the truncated body**
  **Problem:** for statuses outside the switch (e.g. 408/409), `classifyHttpError` keyword-matches the body; "timeout"/"network" past char 300 is now lost. Edge case, but contradicts "classification unaffected".
  **Fix:** `classifyHttpError(response.status, rawErrorText)`.

- [ ] `src/api/graph-files-api.ts:95-97` - **UNC paths dereferenced before rejection**
  **Problem:** `\\attacker\share\x` → `realpath()` opens SMB (NTLM leak) before the containment check rejects it. Not a regression, but cheap to close.
  **Fix:** lexical `relative(resolve(root), resolve(dest))` check before any `realpath`.

- [ ] `src/api/graph-files-api.ts:95` - **Relative path with subdirectory always fails**
  **Problem:** only the root is created; `reports/x.pptx` → ENOENT → INVALID_INPUT, and the agent has no tool to create subdirs.
  **Fix:** `mkdir(dirname(dest), {recursive:true})` after the lexical check, or say "bare file name only" in the tool description.

- [ ] `AGENTS.md:77,119` - **Docs gaps**
  **Problem:** tree omits `src/__fixtures__/isolated-key-store.ts`; TEAMS_HOSTS note doesn't say a missing host now drops the whole region config (all regional APIs fail, not just login detection).
  **Fix:** add both lines.
