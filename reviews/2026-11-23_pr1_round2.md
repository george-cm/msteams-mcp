## Blocking

- [ ] `src/auth/crypto.ts:67` + `src/auth/crypto.test.ts:210` - **CI goes red on Linux**
  CI is `ubuntu-latest` only (`.github/workflows/ci.yml:11`). `path.join` on POSIX joins the path with forward slashes, so the test's backslash `toContain` check fails. Confirmed with `path.posix.join` in Node. The test is also circular: `_dpapiInvocationForTesting()` returns its own copy of the command and cwd, not what `runDpapi` passes to `execFileSync`.
  **Fix:** `path.win32.join(...)`. Have one `dpapiInvocation()` used by both `runDpapi` and the test hook, or mock `child_process` and assert the real call.

- [ ] `src/auth/paths.test.ts:29` - **Fails on Windows when TEMP is the long path**
  `ISOLATED_HOME` is `mkdtemp(os.tmpdir())`, which is under `%USERPROFILE%`. The test passes on George's machine only because `os.tmpdir()` is the 8.3 short name `C:\Users\GEORGE~1.MUR\...` (confirmed). It was reproduced failing with the long-form TEMP.
  **Fix:** assert against the real config dir (`%APPDATA%\teams-mcp-server` or `~/.teams-mcp-server`), not the whole profile.

- [ ] `src/auth/crypto.ts:140` - **Cross-process stale key: `forceNew` still loses the session**
  `resetKeyCache()` only resets the process that ran `clearAllLocalData`. If the CLI runs `login --force` while the server is running, the server keeps old key K1. It can't read the new session and overwrites it with K1, after which nobody can read it. Reproduced (`.tmp/r2/a2_crossproc.ts`). Round 1 named this case.
  **Fix:** remember the loaded `key.dpapi` text; re-read the file each call (cheap, no PowerShell) and reload if it changed or is gone. In `decrypt()`, on a v2 GCM auth failure, `resetKeyCache()` and retry once. Also wrap `rmSync` in try/finally so `resetKeyCache()` always runs.

- [ ] `src/auth/session-store.ts:63-72` - **Half-guard locks users out when DPAPI is permanently broken**
  A v2 file exists and DPAPI fails for good (CLM rollout, admin password reset). `readSecure` returns null, then the login write throws, then a visible browser opens and the write throws again. Only `forceNew` recovers and nothing says so. Meanwhile `token-cache.json` (new file) is written v1 in the same run. Reproduced. **This guard came from OUR round-1 fix suggestion ("never write v1 over an existing v2 file"). Own it in the comment.**
  **Fix:** replace with the policy in `knowledge/decisions/dpapi-failure-policy.md`.

## Warning

- [ ] `src/auth/crypto.ts:176` - **No backoff: a PowerShell spawn per operation**
  Failures are not cached at all, so each read or write spawns PowerShell synchronously. Measured about 1.2-2 s per spawn, up to 30 s on a hang. A token lookup does 2-3 of them, during which the event loop is blocked. A warning is logged on every call too.
  **Fix:** cache `{ failedAt }`; retry after `DPAPI_RETRY_BACKOFF_MS` (60_000, in constants.ts); log once per window.

- [ ] `src/api/graph-files-api.ts:138` - **Recursive mkdir runs before the containment check**
  A junction inside the root lets `mkdir(..., {recursive:true})` create empty directories outside it before the request is rejected. Reproduced.
  **Fix:** realpath the deepest existing ancestor and check containment first; then create the missing segments one at a time, checking each.

- [ ] `docs/SESSION-DATA-REFERENCE.md:485` - **False v1 claim**
  It says v1 files "cannot be decrypted on another computer or user account". The v1 key is scrypt(hostname:username, public salt).
  **Fix:** "v1 is obfuscation, not protection".
